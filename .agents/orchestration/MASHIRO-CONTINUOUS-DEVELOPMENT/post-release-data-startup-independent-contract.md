# Post-release data-location and startup independent repair contract

Read-only diagnosis, 2026-09-08. The user reports a generic startup failure and reuse of acceptance-test data. Historical v0.1.0 qualification is preserved; it does not dismiss this new defect. No current user database, private body, registry or scene was read or changed in this review. The specific startup exception is still unproven and belongs to the native owner's bounded evidence collection.

## Confirmed source seams

- Packaged index.ts calls prepareProductionRuntimePaths before readiness/instance lock. production-bootstrap.ts always uses appData/Mashiro/configuration, runtime and backups. production-session.ts automatically opens a valid READY locator without a selection prompt. The locator and dataset format carry identity/version but no test provenance. Thus a packaged acceptance session using that Windows profile's production selector leaves a valid locator that an ordinary reinstall intentionally reuses. Nonpackaged E2E's owned temporary root does not isolate packaged acceptance. This is distinct from shipping synthetic rows in app.asar; no such packaging leak has been demonstrated.
- Normal production-menu.ts offers current location, backup, copy/relocate, select existing and restore, but no create-new-empty dataset action. It is installed only after AssistantService, ProviderService and the window successfully open, so it cannot resolve failures earlier in startup.
- Bootstrap catches initial session preparation and offers exit/reselect/restore, but a failure from that retry propagates to index's outer catch. Runtime-path preparation and subsequent service/window failures also reach that catch. It discards the error and records only MASHIRO_STARTUP_FAILURE; before app readiness it does not even show the generic dialog. These facts explain poor diagnosis/recovery, not the particular exception reported by the user.

## Minimal implementation contract

1. Preserve ordinary reinstall behavior for a valid real-user dataset. Never infer that all temporary paths, E2E-looking assistant names or the old known test dataset are disposable. The user may already have added real content. Do not delete, clear, silently recreate, or automatically switch their current locator; keep governance/credentials and existing data intact.
2. Add a single trusted data-management entry usable both in a healthy app and startup recovery: display current selected location and dataset identity, select existing, explicitly create a new empty dataset, restore backup, or cancel. A new dataset gets a new ID; it does not copy synthetic rows, connections, credentials or runtime settings. Old data remains in place. A visible confirmation must distinguish new-empty from copy/restore. Successful preparation and writer shutdown/leases precede atomic locator switch; failure/cancellation keeps the original binding. Existing restore governance and pause semantics remain unchanged.
3. Retain error stage plus an allowlisted diagnostic code (filesystem/system code only when safe), and show a useful Chinese reason and explicit recovery actions. Keep raw stack/path/body/credentials out of generic telemetry or renderer IPC. Expose local current-location details only deliberately to the user. Capture failures before readiness and after partial service startup; close acquired services/leases before recovery. A failure to write diagnostics must not mask the original failure. Do not turn integrity/governance/lock errors into empty-data fallback.
4. Isolate future packaged acceptance from the ordinary user's configuration, credentials, runtime, governance and OS integration. Prefer a dedicated Windows test account/profile for the actual release executable and Shell/Run tests: merely another data folder leaves the production locator and registry namespace shared. If a packaged test launch mode is implemented instead, require an explicit trusted owned test root/profile and separate full configuration/runtime/governance namespace; it must never silently override ordinary production launch via inherited E2E environment or renderer input. Shell identity/Run isolation still needs its own solution. No installer change may reset all existing users to force isolation.
5. For this existing contaminated installation, provide explicit non-destructive selection/create controls first. Any one-time operator cleanup requires exact provenance and preservation of subsequent user additions; it is not part of an automatic product migration. Do not hardcode the known synthetic dataset UUID as a disposable-data rule.

## Discriminating acceptance cases (to implement independently)

- Valid ordinary A survives same-version reinstall and restarts on A with unchanged records/locator. A synthetically marked acceptance root lives entirely in the test profile; a subsequent normal launch neither reads nor binds it.
- Legacy shared A containing both synthetic rows and a later user sentinel is not erased or auto-switched. User chooses new empty B: B has a fresh ID/no copied objects or credentials, A including the sentinel remains intact; cancellation and failed B preparation leave A selected.
- Healthy-app new-empty is distinct from relocate/copy; select-existing and backup restore still work through the same quiescent, lease/CAS-governance boundary. Reuse existing later-governance restore fixtures rather than rebuilding their matrix.
- Inject one early configuration-path failure, one session/lease or integrity failure, and one post-session service-open failure. Each produces a bounded stage-specific diagnostic and an accessible recovery/cancel route without data loss, leaked writer or hidden infinite retry. The original exception remains observable after a secondary diagnostics failure.
- Actual packaged ordinary desktop launch in a clean test Windows context opens the intended user-selected dataset; a second launch/reinstall preserves it. Verify the reported real startup failure separately against the native owner's exact error/context evidence; generic dialog text alone is not a root cause.

## 019 implementation seam addendum

Full production-session.ts, production-initialize.ts, production-governance-lifecycle.ts and shutdown/runtime constructors read in 620b1f/890427/a553e2. Recommended createEmpty sequence inside the existing session closure: assertMaintenance and one-operation guard; initializeProductionDataSet using the existing full SqliteStore/integrity/FK callback; retain its returned target lease; recheck assertMaintenance after await; registerPreparedProductionGovernance for the new ID and unregister that transient target registration as select does; locations.bind with openedFingerprint; transfer target to selectedLease for release. Failure releases target, preserves partial/new B and leaves A selected if bind did not commit. Do not call select while already holding the target lease, do not clone A's identity or governance projections, and do not describe cross-file initialization/locator rename as one SQLite transaction. Binding is the commit point; avoid fallible post-commit steps whose error message would falsely promise no switch. Guard a concurrent maintenance call before awaiting initialization.

Failed-start cleanup must stop new IPC/UI work and reminder callbacks, remove registered IPC handlers, close Provider/Assistant writers, then release session governance registrations and selected/data/configuration leases. Never proceed with switching if writer closure is uncertain. startReminderRuntime can throw after creating a tray/listeners but before returning the handle; same-process retry requires local rollback for that partial construction. Otherwise use a clean-process recovery route. AssistantService.open has no local store cleanup if repository construction throws; ProviderService.open closes its store on constructor failure, but this alone is not proof that already-created child timers are stopped. These are bounded ownership checks for the chosen retry design, not a claim that all constructors currently fail in practice.

Use explicit stages such as RUNTIME_PATHS, SESSION_PREPARE, ASSISTANT_OPEN, PROVIDER_OPEN, IPC_REGISTER, WINDOW_LOAD and REMINDER_START; record a correlation ID and allowlisted code, not arbitrary error.message/stack/SQL/secret-bearing values. Secondary cleanup/diagnostics errors must not overwrite the original stage. Current native failure still requires its own causal evidence.
