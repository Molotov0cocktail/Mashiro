## Mechanism verified against Electron 44.1.1

[Electron activator source](https://raw.githubusercontent.com/electron/electron/v44.1.1/shell/browser/notifications/win/windows_toast_activator.cc) writes the raw executable path into LocalServer32 without quotes or custom arguments. It asynchronously ensures the shortcut and registration, then registers and resumes its COM class object. These operations can fail before activation delivery. This is upstream behavior, not proof that this particular bare path caused the failure.

[Application identity source](https://raw.githubusercontent.com/electron/electron/v44.1.1/shell/common/application_info_win.cc) generates a GUID when unset. The activator reads a valid existing shortcut CLSID and sets that value before registering the class, so an ordinary restart should retain current 145B11B4-27B4-4C65-8585-F689F4C2CBB9. A new GUID on every restart is not the normal contract when the shortcut survives. This source was successfully retrieved in this investigation; earlier unavailable-source observations remain historical.

[Microsoft LocalServer32 documentation](https://learn.microsoft.com/en-us/windows/win32/com/localserver32) says COM appends `-Embedding`, passes the resulting command line to CreateProcess, and normally allows 60 seconds for class registration. ServerExecutable can separately specify the executable; without it the application-name parameter is null. Quoting ambiguity is consequently a plausible hypothesis, not a demonstrated defect. No extra Mashiro toast argument is established as required.

Local `index.ts` sets identity before the single-instance lock, then awaits readiness, production preparation and window loading before starting reminder runtime. `recover()` calls `tick(true)`; `runtimeValue()` invokes platform capability detection, which invokes Notification.isSupported and initializes the native presenter. Thus initialization occurs even without a new due reminder, but only after startup work. Electron class registration is additionally asynchronous. Notification.handleActivation installs/replays the callback; it is not itself the presenter initializer. The local second-instance handler merely shows the window; it is not a substitute for COM Activate payload delivery. Only the explicit login argument hides the window. No evidence presently establishes a startup duration over the COM timeout, a lock collision, or an early exception.

The corrected production AUMID and exact AppsFolder target have independent v6 evidence. This failure is not attributed back to the old shared Electron AUMID collision. The current host may be packaged, but existing snapshots do not record the querying helper's package identity; no actual registration-view mismatch has been established. A warm COM result alone cannot settle what a cold SCM sees.
