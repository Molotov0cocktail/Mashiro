# 技术栈与验证选择

## 选型

1. 优先用户指定和团队已掌握的技术；已有 manifest/lockfile 时沿用。
2. 没有既定选型时，选择维护稳定、文档充分、默认安全的最小方案。涉及可能变化的版本时查官方来源，不凭记忆写“最新”。
3. 固定可复现依赖并提交 lockfile；是否精确 pin、允许的运行时范围和升级门禁写入项目规则。
4. 首个里程碑只证明构建链和一个真实行为，不堆功能、数据库、云服务或复杂 CI。

## 环境探测

只运行只读命令并记录退出码：

- OS、架构、shell；
- `git --version` 与当前全局配置中项目真正依赖的项；
- 运行时、编译器、包管理器；
- 必需 SDK/构建工具；
- 项目使用的代理是否可达，但不输出认证信息。

把“要求”与“当前机器观测”分开。禁止擅自安装系统级工具、改全局环境变量、改全局 Git 配置或把机器绝对路径写进可移植项目文件。

## 验证分级

| 变更 | 最低检查 |
| --- | --- |
| 纯文档 | 链接/路径/命令一致性、格式、diff、敏感信息 |
| 纯逻辑 | 甄别性测试、全量测试、类型/lint/格式、diff |
| UI/进程/IO | 上述检查 + 构建 + 真实启动或冒烟 |
| 数据/迁移/权限/安全 | 上述检查 + 敌手矩阵、失败/恢复、独立高推理复核 |
| 发布 | 当前交付物重建、制品检查、远程/下载验证；需要显式发布授权 |

行为变化通常采用红→绿：先建立旧实现失败、新实现能通过的 oracle。纯文档、机械格式或无法稳定自动复现的环境问题可以采用结构检查、诊断探针或明确的人工步骤，但必须解释为何没有红态测试。

## 基线验收

1. 从干净环境可安装或恢复依赖。
2. 最小入口能构建/启动。
3. 至少一个测试验证真实结果，不只断言 mock 被调用。
4. 配置中的测试、类型、lint、格式和构建命令与文档相同。
5. `git diff --check` 和状态复查无敏感信息、缓存、日志、截图、临时脚本或构建产物。
6. 失败项按 `FAILED` 或 `NOT RUN + 原因` 报告，不能用空测试或跳过伪装成功。
