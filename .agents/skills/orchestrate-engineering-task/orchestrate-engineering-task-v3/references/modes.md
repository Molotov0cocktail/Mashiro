# 任务模式路由

## 先判断授权

| 用户意图 | 默认权限 |
| --- | --- |
| 回答、解释、检查、评审、报告状态 | 只读调查与验证；不修改、不提交、不 push |
| 诊断、找根因 | 只读复现和定位；未明确要求修复时不改产品代码 |
| 计划、设计、拆任务 | 可更新用户要求的计划产物；产品代码默认只读 |
| 实现、修复、重构 | 可在请求范围内改代码、测试、必要文档和本地 commit |
| 全委派、持续开发、自动推进 | 可自动规划、探索、实现、复核、收尾和选择下一里程碑；commit、push、付费调用等按持续授权执行 |
| 收尾、发布、部署 | 只执行当前项目规则或用户明确/持续授权的外部动作；push 与 Release/部署分开判断 |
| 监控、等待 | 使用平台等待/自动化能力；不用无界阻塞循环冒充进展 |

授权必须结构化理解，至少区分：

```text
LOCAL_WRITE
GIT_COMMIT
GIT_PUSH
DEPENDENCY_NETWORK
PAID_PROVIDER_CALLS
REQUEST_CREDENTIALS
RELEASE_DEPLOY
PERSONAL_DATA_ACCESS
SYSTEM_LEVEL_CHANGE
```

某项已获持续授权后，在授权范围和接收方不变时不得逐次询问。未获授权的其他项不能由相邻授权推断，例如允许 `git push` 不等于允许创建公开 Release，允许合成 Provider 调用不等于允许发送真实个人数据。

## 模式

### Inspect / Explain

读取权威文件、代码和必要机器状态，直接给证据结论。不要创建 Execution Contract 或子 Agent，除非问题本身跨域且用户要求。

### Plan / Design

由高推理角色澄清目标、非目标、方案权衡、决策所有权、安全/数据边界、验收 oracle、路线切换条件和任务依赖。默认不改产品代码。输出正式设计变更建议与 Execution Contract。

### Explore / Spike

用于未知 API、依赖兼容、架构可行性或根因假设比较：

1. 在临时目录、独立分支/worktree 或明确隔离范围内运行；
2. 每个实验只回答一个可判定问题；
3. 记录假设、输入、第一错误状态和证据增量；
4. 可以快速重写和丢弃，不要求完整候选审计；
5. 成功结果必须由 Planner 转化为正式候选合同后才能进入产品主线。

探索失败默认是 `REPLAN` 输入，不是 `BLOCKED`。

### Execute Feature

先确认合同、路线和 baseline，再由执行角色小步红→绿实现、运行聚焦与风险相称的验证、审阅 diff，并按授权形成候选提交。实现者不自判 `PASS`。若合同允许候选分支 push，可执行，但不得把已推送等同于已验收。

### Diagnose Bug

由高推理角色：

1. 固定版本、运行形态和症状；
2. 优先读受控日志并最小复现；
3. 沿真实调用链定位第一个错误状态；
4. 区分产品、测试夹具、环境、依赖和外部服务；
5. 解释旧测试为何未阻止；
6. 输出根因证据、未知项和有界修复或替代路线。

若用户只要求诊断，到此停止；在持续开发模式下则自动进入 Fix 或 REPLAN。

### Fix Bug

先完成诊断。执行角色建立复现失败的 oracle，做最小修复，检查同模式风险但不顺手扩大修复。涉及交付物时重新构建并验证制品包含修复。

### Refactor

冻结可观察行为与覆盖测试；逐步提交，每步独立可回退。不要把重构与功能/bug 混成一个不可审 diff。

### Review

高推理 Reviewer 从精确 baseline 审查 `baseline..HEAD` 与工作区，读关键代码和测试并独立复跑风险相称的验证。结论只能是：

- `PASS`：当前候选满足合同；
- `REPAIR`：设计和路线不变，一次有界修复即可；
- `REPLAN`：合同、架构、依赖、路线或 oracle 必须重做；
- `BLOCKED`：缺少无法由工程链替代的外部事实、凭据、权限或环境。

技术路线失败、测试夹具失败、未知 API 行为、依赖冲突和实现困难都应是 `REPLAN`，不能写成 `BLOCKED / REPLAN REQUIRED` 之类复合 verdict。

### Route Assessment / Replan

由全新高推理角色读取尝试账本和原始证据，判断：

- 是否只是瞬时失败，可做一次相同条件重试；
- 是否应修正实现而保留路线；
- 是否应替换依赖、API、进程模型、数据结构或验证方法；
- 某辅助门禁是否超出产品 acceptance，应降级为非阻塞审计；
- 是否需要缩小问题、先做 spike，再形成新合同；
- 是否真的触发用户拥有的产品决策。

相同 first bad state 在同一路线重复两次，或同一路线累计三次失败实现/修复循环时，必须执行本模式。两条实质不同路线均失败后，再启动独立架构评估；只要存在有价值的新证据或合理替代路线，不设全局尝试次数和任务总时限。

### Security / Migration / Stage Audit

使用全新、独立的高推理上下文；覆盖敌手输入、失败原子性、恢复、数据不变量、权限、隐私扫描和真实运行条件。只在高风险边界或阶段 Exit Gate 使用，不对每个探索实验机械套用完整审计。

### Repair

执行角色只处理 Reviewer 的 Repair Contract，追加可审查修复，不重开设计、不重写候选历史。相同根因连续两轮仍未关闭时必须 `REPLAN`，不得继续同一路线机械修补。

### Close

执行角色仅在 `PASS` 与审核 HEAD 完全匹配时更新短期事实源、执行最终状态检查、创建确定性收尾提交，并按 `EXTERNAL_ACTION_POLICY` 自动 push、同步远程或执行其他已授权动作。Release/部署未授权时明确保留，不因 push 已授权而推断。

### Autonomous Development

用于用户明确要求全委派、持续推进或 Prompter 自动化：

1. 先调和项目真实状态、旧报告和路线图；
2. 选择一个连贯且可验收的当前里程碑；
3. 按需要运行 Planner、Explorer、Executor、Reviewer、Repair/Replan 和 Closer；
4. 一个里程碑 PASS 后自动选择下一个不需要新产品决策的高价值任务；
5. 只有真实用户门禁、无可继续的未阻塞任务或可靠性要求的检查点才返回用户。

持续模式不意味着降低验证，也不意味着每个细节都做最高等级验证。目标是在产品风险相称的证据下持续交付，而不是让验证基础设施本身无限扩张。

## 失败与挂起

- 不设置任务级总时限。
- 单个命令、测试、网络请求、模型调用和子进程应有技术超时，以便识别挂死并回收资源。
- 相同命令只在存在瞬时故障证据时机械重试一次。
- 每次失败必须记录 `ROUTE_ID`、尝试编号、first bad state、证据增量和下一假设。
- 同一失败无证据增量地重复两次，必须换诊断方式或路线。
- 非产品核心的附加审计失败可由高推理 Reviewer/Planner降级为已知风险或后续任务，不能自动冻结整个项目。

## 风险分级

- **低**：文案、局部纯逻辑、无公共接口/持久化/外部副作用。可同一上下文规划与执行，但仍需可复核验证。
- **中**：多文件行为、UI/IO、公共接口或重要回归。Planner/Executor/Reviewer 分工更合适。
- **高**：安全、隐私、权限、迁移、持久化、并发、公开发布、不可逆动作、架构或阶段 Exit Gate。必须全新独立高推理 Reviewer；需要恢复、敌手和真实条件证据。

流程重量取决于风险、歧义和 acceptance，不取决于改动行数。纯文档不应机械跑产品全套冒烟；一行权限变化也可能需要最高等级。
