## 当前 F1 架构落点

- 当前实际链路是 React renderer → contextBridge preload → 六个 typed assistant IPC handler → trusted AssistantService/Repository → Electron main 的 `node:sqlite`。
- preload 的运行时依赖图只有 Electron 与无 Zod 的本地通道常量；Zod strict input/output/result schema 留在 trusted contract/main 验证路径，畸形输出不会跨 IPC。窗口固定 `contextIsolation=true`、`sandbox=true`、`nodeIntegration=false`、`webSecurity=true`，并拒绝新窗、导航和权限请求；启动失败日志只含固定脱敏事件名。
- SQLite schema/version/trigger guard、参数化语句、`BEGIN IMMEDIATE` 事务、stable UUID、assistant/state revision 和 primary/current active invariants 已实现并有 adversarial、stale/concurrent、rollback、corrupt/newer schema 测试。
- E2E 数据根必须是带 runId 所有权标记的 canonical OS-temp 子目录；开发数据位于 appData 的 `Mashiro Development`。真实 Electron seed/verify 使用不同 PID 并证明相同持久化快照；本轮 Candidate Reviewer 的独立完整 `verify` 使用 PID `506244 → 506388`，并对 reviewed HEAD 给出 `PASS`。
- Provider、memory、item、reminder、worker、托盘、安装/更新/迁移和 `PACKAGED` 仍不属于当前实现。

## 1. 架构目标

Mashiro 首版是一个 Windows 桌面应用：Electron＋TypeScript＋React，无独立 Windows 常驻服务，也不要求生产运行依赖自托管本地 HTTP 服务器。窗口关闭后可驻留托盘；明确退出后停止本应用后台作业和受管理辅助进程。

架构优先保证：

1. 本地数据权威与可迁移；
2. renderer 与凭据、文件、数据库、系统能力隔离；
3. 权限在每次读取、外发和业务提交时由程序执行；
4. Provider 差异显式、可验证、可降级；
5. 模型失败不破坏已有有效数据或确定性本地能力；
6. 不为远期集成提前引入分布式服务、通用 Agent 框架或空接口层。

## 2. 进程与依赖方向

```text
React renderer（不可信展示与用户意图）
  → 受限、类型化 preload bridge
    → Electron main 中的应用用例与权限检查
      → 领域模块 / 可信存储 / 凭据代理 / Provider 客户端 / 调度器
        → 本地数据目录、Windows 凭据保护、获准的远端端点

耗时或同步工作
  → 由 main 受控调度到 worker/辅助进程（按实测决定）
```

确认边界：

- `contextIsolation`、renderer sandbox 与窄 IPC 是稳定安全约束。
- renderer 不获得任意文件路径、SQL、完整凭据、通用命令执行或任意网络代理能力。
- 模型输出、用户资料、Markdown、远端响应和导入文件均视为不可信数据，不作为代码执行。
- 工作线程属于可信侧的受管理执行位置；“可信侧控制”不等于所有工作永远在 UI 或 main 线程同步完成。

## 3. 模块职责

以下为职责边界，不代表本次初始化会创建全部目录或模块。

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| Assistant | 稳定助手身份、配置、归档、主助手、数据范围 | 自动多助手协商 |
| Conversation | 每助手唯一时间线、章节、上下文构建、严格临时模式 | 全局用户事实权威 |
| Provider | 连接、模型选择、能力证据、请求适配、流式与用量解析 | 决定业务操作授权 |
| Permission | 读取权、接收方外发权、业务操作政策与动态撤权 | 依赖 Prompt 自律 |
| Credential | Windows 保护的持久凭据与运行期临时凭据 | 明文导出或跨机器可解密承诺 |
| Memory | 助手连续性记忆、全局 Markdown 分支、来源、性质与状态 | 把推测升级为事实 |
| Warehouse | 受预算和权限限制的全局增量整理 | 用户对话角色或通用 Agent |
| Personal Event | 意向、安排、报告发生、完成、取消等可追溯事件 | 替代正式任务或 Clender 日历 |
| Item | 目标、项目、任务、承诺、等待事项和待确认提案 | 建立第二套日历 |
| Reminder | 确定性提醒、补发候选和运行承诺 | 明确退出后的持续保证 |
| Operation | 工具意图、稳定操作身份、结果与恢复状态 | 用日志代替业务事实 |
| Health / Usage | 当前状态、历史故障、调用用量、预算和恢复入口 | 保存正文或密钥 |
| Data Location | 解析、验证并绑定程序目录和数据目录 | 静默切换或创建第二份空数据 |

## 4. 数据权威与派生关系

```text
本地事务存储
  ├─ 助手、时间线、事项、提案、提醒、操作、作业
  ├─ 记忆身份、来源、性质、权限、版本、生效/抑制状态
  └─ Provider 配置元数据、能力证据、协议段索引、用量状态

Markdown 记忆分支
  └─ 可读、可编辑、可导出的长期记忆语义正文与分支组织

派生索引
  ├─ 全文索引
  └─ 可选 embedding / 向量索引
```

确认规则：

- Markdown 与事务状态是职责分工，不是同一字段的两个可独立修改权威。
- 出现版本或对应关系不一致时，限制受影响部分的召回、外发和写入，不能任取一方或混用版本。
- 派生索引可重建；索引失败不能删除有效记忆，向量相似度不能作为事实置信度。
- 只导出 Markdown 正文不等于完整迁移备份；权限、来源、版本和删除抑制须由完整迁移格式承载。
- 应用内编辑为首版主路径；外部 Markdown 修改须显式重新载入、差异检查和验证，不能扩大权限。

## 5. 主要数据流

### 5.1 正常对话

1. renderer 提交用户意图和当前助手稳定 ID。
2. main 读取当前助手、时间线和权限状态。
3. Context Builder 只选择任务所需且允许读取的数据。
4. Permission 再检查目标端点获准接收的数据类别。
5. Provider Adapter 根据端点、模型、模式和已验证能力构建请求。
6. 流式或普通响应进入规范化解析；工具调用必须完整组装后进入执行检查。
7. 用户可读消息、协议续接数据、记忆增量和运行日志分别写入各自职责区域。

### 5.2 严格临时模式

1. 只加载助手稳定人设和所选 Provider 配置。
2. 不读取正常时间线、个人/关系记忆或业务上下文。
3. 续接与正文仅在允许的内存范围内处理。
4. 不创建时间线消息、记忆、事件、事项、提案、提醒或可重启快照。
5. 用户明确保存时，先通过可理解的模式切换/保存流程，再按正常权限执行。

### 5.3 记忆整理

- 助手维护自己的章节、关系记忆、连续性摘要和未完成话题，并把适合全局资料的增量连同来源和内容性质提交待整理区。
- 内置仓储员在已授权条件、预算和范围内处理增量、去重、归并、分支整理和冲突识别。
- 用户明确记住、纠正或删除有即时生效路径，不等待下一轮周期整理。
- 自动整理不能改变内容权限、来源归属或把新增推断升级成用户事实。

### 5.4 工具与业务操作

```text
模型提出 tool_call
  → 协议完整性检查
  → 工具名和参数 Schema 检查
  → 当前权限与对象状态检查
  → 建立稳定 operation identity
  → 执行或等待确认
  → 记录实际结果/未知状态
  → 按当前外发权限把结果回传给同一执行段 Provider
```

模型请求重试与业务恢复相互独立。已经成功创建事项但最终自然语言回复中断时，系统展示真实业务结果和回复中断状态，不再次创建事项。

### 5.5 提醒

- 正式提醒从本地权威事项和提醒状态产生，不依赖模型在线。
- Provider 凭据缺失可以暂停模型后台功能，但不能使已保存的确定性提醒失效。
- 启动、托盘、休眠恢复和重启补发遵守已确认运行承诺；明确退出后不承诺继续提醒。

## 6. Provider 兼容架构

### 6.1 已确认协议方向

- Chat Completions 优先，不自动试探 Responses，不因失败静默改变端点或接收方。
- DeepSeek、GLM 为首批重点目标；Qwen、Kimi参与差异审查；MiniMax、Gemini、Claude先记录限制。
- 允许内置、可测试的有限厂商适配，处理思考参数、输出字段、工具限制和用量差异；不开放任意请求模板或脚本。
- 模型 ID 不是永久能力依据；普通、流式、思考、工具、strict、并行工具、结构化输出和用量分别记录证据。

### 6.2 规范化与保真

推荐／待评审：Provider 层采用“公共语义＋受控厂商扩展”的内部消息表示。

- 公共语义服务于用户消息、助手消息、工具调用、工具结果、结束原因和用量。
- 厂商要求原样回传的 `reasoning_content`、签名或扩展片段保存在受控协议段，不塞入普通聊天文本。
- 适配器只接收允许的明确扩展键；未知响应字段可用于诊断或资格测试，但不自动进入持久化正文。
- 活动工具链不裁剪半条消息、不重排调用与结果；能否重建新协议段由具体端点/模型规则和测试决定。

### 6.3 能力证据

能力状态至少区分：

- `DOCUMENTED`：官方文档声明；
- `LOCAL_TESTED`：本地协议与解析测试通过；
- `LIVE_VERIFIED`：用户授权的具体端点真实调用通过；
- `UNKNOWN`、`UNSUPPORTED`、`TEMPORARY_FAILURE`、`MISCONFIGURED`：避免把一次失败永久解释成不支持。

证据绑定端点指纹、协议、模型/版本、模式、适配版本、测试时间和结果。端点接收方或路由变化时重新检查授权和证据。

## 7. 生命周期与保留

### 7.1 记忆与个人事件三区

- 持久保留区：受容量限制，但不因时间、排序或模型判断自动降级或删除。
- 暂存区：近期或价值待定内容，可按授权整理到持久区或垃圾区。
- 垃圾区：退出正常召回、上下文和后台摘要，仍是已保存数据，可恢复或批量清空。

分区不改变用户陈述/归纳/推测性质、证据支持、助手归属、读取范围或外发权限。

### 7.2 聊天原文

- 上下文压缩与本机原文回收是不同动作。
- 回收前须确认接受的事件、摘要和连续性记忆已保存，未完成话题和待处理操作不再依赖原文，且不会覆盖用户纠正或删除。
- 默认采用可恢复阶段；整理失败、保存失败或依赖未满足时不回收。
- “整理回收原文”可保留接受的派生信息；“删除信息/撤回依据”按用户意图处理原文、事件、记忆、摘录、版本和索引，并执行防复活规则。

### 7.3 协议执行数据

- 正常模式按需保存恢复和续接必需字段，和聊天、记忆、日志分开。
- 严格临时模式不建立可重启的正文或协议快照。
- 删除、撤回来源或撤销外发权限时，相关协议数据同样受影响；无法合法续接则暂停或结束。

## 8. 数据位置与凭据

- 默认使用当前 Windows 用户的标准程序目录和数据目录。
- 安装时允许分别自定义程序位置和数据位置，也允许把数据放在安装目录下的 `data` 子目录。
- 所选数据目录须按日常普通用户权限验证；安全或持久化无法保障时阻止继续，不以管理员安装成功替代运行期验证。
- 位置失效、权限变化或空间不足时明确报错，不静默回退、创建空数据或覆盖数据库。
- 开发、测试、正式数据隔离；源码仓库不得存放真实聊天、记忆、凭据或运行日志。
- Windows 凭据保护位置可作为必要例外；自定义 data 不等于凭据可跨用户或跨机器解密。

推荐／待评审：使用标准用户配置位置中的最小 locator 记录所选数据根和数据集身份，数据根保存匹配的 manifest。启动时两者不一致或不可用则进入恢复流程，不自动创建新数据集。具体 Windows API、文件格式和迁移规则待实现任务冻结。

## 9. 失败、恢复与取消

- 本地数据库内的业务修改与结果记录优先共同事务提交；不把该保证扩大到 Markdown 或外部服务。
- 对跨文件或未来外部调用，持久化稳定操作身份，恢复时先核查结果：确认成功则不重做，确认未发生才评估继续，未知则核查或提示。
- 幂等性由程序契约和测试证明，不能由模型自行声明。
- 一次执行段固定端点、协议、模型、模式和适配语义；普通配置变化下段生效，撤权、连接禁用或凭据删除在每次新调用和业务提交前即时检查。
- 取消停止派发未开始操作并尽力中断在途调用；不承诺远端绝对停止、未计费或全部回滚。

## 10. 运行状况、日志和用量

- 用户记忆来源/变更记录、业务操作记录和开发运行日志是不同数据职责。
- 运行状况页面区分历史事件与当前状态，默认显示 WARN 及以上，并展示等待、运行、重试、待配置、失败或恢复。
- 后台重复错误合并；持续失败、需用户处理或影响重要功能时明确提醒。
- 日志默认只记录事件、关联标识、状态、耗时和可用用量，不复制正文、原始请求响应、密钥或认证信息。
- 用量按助手、Provider/模型和功能区分，并标记实际、估算或未知；缺失 usage 不记为零，没有可靠价格依据不展示准确账单。

## 11. 主要权衡

| 方案 | 当前结论 | 收益 | 代价/风险 |
| --- | --- | --- | --- |
| Electron＋TS＋React | CONFIRMED | 延续现有经验，适合 Windows UI | 资源占用与原生依赖需实测 |
| 单应用、无独立服务 | CONFIRMED | 部署和数据边界简单 | 明确退出后无后台保证 |
| SQLite＋Markdown分工 | CONFIRMED 方向 | 事务状态与可读语义兼得 | 跨层一致性需专门恢复设计 |
| `node:sqlite` | 待验证首选 | 避免额外原生 addon | 取决于 Electron 内嵌 Node 与实际能力 |
| Chat Completions优先 | CONFIRMED | 广泛兼容当前目标服务 | 部分厂商原生高级能力后置 |
| 本地会话权威 | CONFIRMED | 可迁移、权限可控 | 上下文构建和 token 成本更高 |
| 直接 HTTP＋小型 SSE 解析器 | 推荐／待评审 | 扩展字段与重试控制透明 | 流式与错误解析测试责任更大 |
| OpenAI Node SDK 作为传输 | 备选／待评审 | 基础协议与流式实现成熟 | 默认重试、类型和厂商扩展需逐版本核查 |

Provider 客户端选择不是当前初始化的必然阻塞；若初始化闭环不包含网络对话，可在下一独立任务中冻结。

## 12. 测试策略

- 纯领域逻辑：状态机、权限交集、删除抑制、用量累计和能力证据使用甄别性单元测试。
- IPC：验证 renderer 只能调用允许的意图，输入经过运行时 Schema 校验，错误不泄露秘密。
- 存储：事务提交/回滚、迁移、重开、并发策略、路径失效和恢复。
- Provider：合成 SSE、分段 tool arguments、独立 usage 片段、思考字段续接和完整无副作用工具闭环。
- UI：基础可读、操作可完成、状态与错误可理解；不以最终视觉为本阶段验收。
- 进程/IO：构建后实际启动或冒烟；同步或耗时任务的响应性按任务设置阈值并实测。
- 安全/恢复：取消、撤权、崩溃窗口、重复派发、严格临时无持久快照和敏感日志检查。

测试工具和精确版本尚未冻结。推荐／待评审：Vitest 承担纯逻辑和集成测试，React Testing Library 承担 renderer 行为；Electron 实际启动工具在锁定 Electron 版本后核对维护状态与兼容性。

## 13. 后续集成边界

- AIbrowse：保持完整浏览器与研究 AI；未来通过受控工具或任务委托接入，并按规则提交统一记忆增量。当前不冻结通信协议。
- Clender：继续作为唯一真实日历状态的展示、保存和手动调整端；Mashiro 当前只管理事项及提醒，不建立竞争日历。此前只读代码审阅只发现 REMINDER/TIMESPAN 类日程事件，未发现独立任务/目标子系统；该证据只描述当时版本，未来接入前必须重新核验最新代码与数据模型。
- 个人数据源：每类来源单独定义读取、摘要、记忆、助手访问和远端外发权限，日记等敏感数据单独控制。
- Responses、Claude Messages及其他厂商原生协议：在共同 Chat Completions 基线稳定后独立评估，不由现有适配器自动猜测。
